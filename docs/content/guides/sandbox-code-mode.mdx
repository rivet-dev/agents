In code mode, the model writes a program that calls tools instead of calling them one at a time. This guide runs that program in the agent's sandbox. When the agent connects, it writes `call-tool.sh`, a shell script that calls the agent's actions with a [scoped JWT](/docs/jwt). The model uses each action as a tool, and your Rivet token stays on your worker.

## Why run code mode in the sandbox

Code mode gives an agent an "execute script" tool that lets it write JavaScript to call your tools. That script usually runs in a tiny embedded JavaScript runtime such as QuickJS, cut off from the system it's working on. It can't:

- Save scripts that call your tools and reuse them later
- Use npm or PyPI packages installed on the system
- Use a rich standard library, such as Node's or Bun's `fs`, streams, and `child_process`
- Work with files too large to load into memory
- Call tools in the background after the turn ends, such as from a file watcher or a long job

A script in the sandbox runs on that system, so it can do all of this, but it can't reach your tools:

`call-tool.sh` closes the gap. The program runs in the sandbox next to your files and packages, and each tool call goes to an action in your backend, where the keys are.

Use it when a script calls tools in a loop, or when sandbox work should reach your app. If the model calling tools one at a time is enough, use [Custom Tools](/agents/docs/custom-tools).

## Why not put the agent in the sandbox

Running the whole agent inside the sandbox would also put the tools next to the files, but the sandbox is the wrong place for the agent:

- **A broken sandbox takes the agent with it.** An out-of-memory build or a corrupted filesystem kills the agent loop and its history. Here Pi runs in the agent Actor and keeps the conversation in its own database.
- **Anything in the sandbox can leak.** Model keys and tool credentials would sit next to untrusted code. Here they stay on your worker, and the sandbox holds only a token for one agent.
- **Sandboxes sleep.** Schedules, workflows, and reading history shouldn't wait for a sandbox to start.

See [Run Your Harness Outside the Sandbox](/blog/2026-07-27-run-your-harness-outside-the-sandbox) for the full argument.
