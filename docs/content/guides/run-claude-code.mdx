Run Claude Code for your users in cloud sandboxes, with one Rivet Actor per session that remembers the conversation and the sandbox.

What we'll build:

- A `claudeSession` Rivet Actor per session, keyed by your session id, that stores the transcript, the sandbox id, and Claude Code's own session id.
- An E2B sandbox per session, created through the sandbox adapter, with Claude Code installed on first use.
- A `prompt` action that runs `claude -p` with `exec` and streams each JSON event to connected clients as it arrives.
- Follow-up prompts that reconnect to the same sandbox and resume the same Claude Code session.

<Steps>

<Step title="Install">

```sh
npm add @rivet-dev/sandbox-adapter e2b rivetkit
```

Claude Code itself isn't installed on your worker. Each sandbox installs its own copy.

</Step>

<Step title="Set the keys">

Create an API key in the <a href="https://e2b.dev/dashboard" target="_blank" rel="noopener noreferrer">E2B dashboard</a> and one in the <a href="https://platform.claude.com" target="_blank" rel="noopener noreferrer">Claude Console</a>, then set both on your worker:

```sh
E2B_API_KEY=e2b_...
ANTHROPIC_API_KEY=sk-ant-...
```

The E2B key never enters the sandbox. The Anthropic key reaches only the Claude Code process, as the next step shows.

</Step>

<Step title="Build the command">

`cli.ts` holds everything that is specific to Claude Code: how to install it, how to run it without a terminal, and how to read what it prints:

<CodeSnippet file="examples/docs/run-claude-code/cli.ts" title="cli.ts" highlight="command,events" />

- `INSTALL` runs Claude Code's native installer, which puts the CLI at `~/.local/bin/claude`. The `test -x` check skips the download when the sandbox already has it.
- `-p` runs one prompt and exits. `--output-format stream-json` prints every message, tool call, and the final result as one JSON line, and Claude Code requires `--verbose` alongside it.
- `--dangerously-skip-permissions` lets Claude Code edit files and run commands without asking, because nobody is there to approve them. The sandbox is the boundary.
- `--resume` continues the conversation from an earlier run. Claude Code keeps its sessions under `~/.claude` inside the sandbox, so this works for as long as the sandbox exists.
- `readEvent` takes the session id from any event and the answer from the last event, `result`.

<Warning>
`cliEnv` passes `ANTHROPIC_API_KEY` in the `env` of a single `exec` call. The provider hands it to that one process, and it is never written to the sandbox's disk. Commands that Claude Code runs inherit it, though, so code in the sandbox can read it. Give the sandbox a key with a spending limit.
</Warning>

</Step>

<Step title="Create the session Actor">

Each session is a `claudeSession` Actor, keyed by your session id:

<CodeSnippet file="examples/docs/run-claude-code/session.ts" title="session.ts" highlight="state" />

- `state` is saved with the Actor, so it survives sleep, crashes, and upgrades. It holds the transcript, the session's sandbox id, and the id Claude Code gave its own session, which is different from your session id.
- `output` is the event that carries Claude Code's JSON events to every connected client.
- `running` lives in `vars`, which are not saved. It stops a second prompt from starting a second Claude Code in the same sandbox while the first one works.
- `actionTimeout` raises RivetKit's 60-second limit on an action, because one coding task can take many minutes.

<Warning>
Any client that knows a session id can prompt it, and every prompt runs commands with your API key. In production, protect the Actor with [authentication](/docs/authentication).
</Warning>

</Step>

<Step title="Connect the sandbox">

The Actor creates its sandbox on the first prompt and reconnects to it on every prompt after that:

<CodeSnippet file="examples/docs/run-claude-code/session.ts" title="session.ts" highlight="provider,sandbox,lifecycle" />

- `e2bProvider` starts sandboxes from E2B's `base` template. E2B stops a sandbox when its timeout runs out, so the one-hour timeout covers a long task, and the provider pauses the sandbox at the timeout instead of deleting it.
- `openSandbox` connects with the stored id. On the first prompt, or after the provider has deleted the sandbox, it creates a new one, saves its id, and clears Claude Code's session id, since the new sandbox has none of the earlier files.
- `INSTALL` runs on every connect but returns right away once Claude Code is installed, so an install that failed partway is retried on the next prompt.
- `onSleep` pauses the sandbox while the Actor sleeps. The next prompt resumes it with its files and Claude Code's sessions intact. `onDestroy` deletes it.

<Note>
agentOS can't run Claude Code, because it only runs software from its own registry, not binaries downloaded with `curl`. Daytona can: pass `daytonaProvider()` from `@rivet-dev/sandbox-adapter/daytona` instead, but Daytona returns a command's output only when it exits, so clients get the events all at once at the end. Freestyle runs commands as root, and Claude Code refuses `--dangerously-skip-permissions` as root. See [Providers](/agents/docs/sandboxes#providers).
</Note>

</Step>

<Step title="Run a prompt">

The `prompt` action runs Claude Code once and streams what it prints:

<CodeSnippet file="examples/docs/run-claude-code/session.ts" title="session.ts" highlight="prompt" />

- `exec` runs the command in the sandbox's working directory. Its `onData` callback receives output as the sandbox reports it, and `jsonLines` turns that into one event per JSON line.
- Each event is broadcast to connected clients right away, so your app can show tool calls and messages while Claude Code works.
- The first event carries Claude Code's session id, which the Actor saves so the next prompt passes it to `--resume`.
- The transcript gets the prompt and the final answer only after Claude Code exits cleanly. A failed run throws a `UserError` that the client receives with the reason.
- `c.abortSignal` stops Claude Code if the Actor shuts down mid-run, and `timeoutMs` stops it if it runs too long.

</Step>

<Step title="Try it">

Register the Actor and start the worker:

<CodeSnippet file="examples/docs/run-claude-code/server.ts" title="server.ts" />

```sh
npx tsx server.ts
```

In another terminal, connect to a session and send a prompt and a follow-up:

<CodeSnippet file="examples/docs/run-claude-code/client.ts" title="client.ts" />

```sh
npx tsx client.ts
```

The first prompt takes longer because it creates the sandbox and installs Claude Code. The follow-up reuses both and continues the same conversation, so "it" refers to `fib.py`. Run `client.ts` again later with the same session id and it picks up where it left off. Call `getTranscript` to show the earlier turns.

</Step>

</Steps>
