### What we'll build

- An `ampSession` Rivet Actor per session, keyed by session id, that stores the transcript and the sandbox id.
- A sandbox for each session from the sandbox adapter, with the Amp CLI installed when the sandbox is created.
- A prompt action that runs `amp -x` with `exec` and streams its output to the client.
- Follow-up prompts that reconnect to the same sandbox and continue the same Amp thread.

### Similar tools

This is the same job as running Amp in CI or driving it with the Amp SDK. On Rivet, each session is an Actor with its own sandbox id and transcript, so your app can start many sessions, leave them, and come back to any one by key.

### Open questions

- Which providers can run the Amp CLI. E2B and Daytona can run it in a full Linux image; whether agentOS runs it is not confirmed.
- How the Amp API key reaches the sandbox, for example as an `exec` environment variable, without being written to the sandbox's disk.
