Run the Amp CLI for your users in cloud sandboxes, with one Rivet Actor per session that remembers the conversation and the sandbox.

What we'll build:

- An `ampSession` Rivet Actor per session, keyed by your session id, that stores the transcript, the sandbox id, and the id of the Amp thread.
- An E2B sandbox per session, created through the sandbox adapter, with the Amp CLI installed on first use.
- A `prompt` action that runs `amp -x` with `exec` and streams each JSON event to connected clients as it arrives.
- Follow-up prompts that reconnect to the same sandbox and continue the same Amp thread.

<Steps>

<Step title="Install">

```sh
npm add @rivet-dev/sandbox-adapter e2b rivetkit@3.0.0-preview.1
```

The Amp CLI itself isn't installed on your worker. Each sandbox installs its own copy.

</Step>

<Step title="Set the keys">

Create an API key in the <a href="https://e2b.dev/dashboard" target="_blank" rel="noopener noreferrer">E2B dashboard</a> and an access token in your <a href="https://ampcode.com/settings" target="_blank" rel="noopener noreferrer">Amp settings</a>, then set both on your worker:

```sh
E2B_API_KEY=e2b_...
AMP_API_KEY=sgamp_...
```

The E2B key never enters the sandbox. The Amp token reaches only the Amp process, as the next step shows. Use an access token from settings. The CLI rejects the short-lived token that `amp login` saves.

</Step>

<Step title="Build the command">

`cli.ts` holds everything that is specific to Amp: how to install it, how to run it without a terminal, and how to read what it prints:

<CodeSnippet file="examples/docs/run-amp/cli.ts" title="cli.ts" highlight="command,events" />

- `INSTALL` runs Amp's install script, which puts the CLI at `~/.amp/bin/amp`. The `test -x` check skips the download when the sandbox already has it.
- `-x` turns on execute mode: Amp sends the prompt, waits for the agent to finish its turn, and exits. `--stream-json` prints every message, tool call, and the final result as one JSON line, in the same shape as Claude Code's stream JSON.
- Amp doesn't ask before running tools by default, so the command needs no flag to skip approvals. The sandbox is the boundary.
- `threads continue` with a thread id sends the prompt to an existing thread instead of starting a new one. Amp stores threads on its own servers, not in the sandbox.
- `readEvent` takes the thread id from any event, which Amp names `session_id`, and the answer from the last event, `result`.

<Warning>
`cliEnv` passes `AMP_API_KEY` in the `env` of a single `exec` call. The provider hands it to that one process, and it is never written to the sandbox's disk. Commands that Amp runs inherit it, though, so code in the sandbox can read it and spend from your Amp account. Use a token from an account or workspace you're willing to expose to the sandbox.
</Warning>

</Step>

<Step title="Create the session Actor">

Each session is an `ampSession` Actor, keyed by your session id:

<CodeSnippet file="examples/docs/run-amp/session.ts" title="session.ts" highlight="state" />

- `state` is saved with the Actor, so it survives sleep, crashes, and upgrades. It holds the transcript, the session's sandbox id, and the id of the Amp thread, which is different from your session id.
- `output` is the event that carries Amp's JSON events to every connected client.
- `running` lives in `vars`, which are not saved. It stops a second prompt from starting a second Amp in the same sandbox while the first one works.
- `actionTimeout` raises RivetKit's 60-second limit on an action, because one coding task can take many minutes.

<Warning>
Any client that knows a session id can prompt it, and every prompt runs commands with your Amp token. In production, protect the Actor with [authentication](/docs/authentication).
</Warning>

</Step>

<Step title="Connect the sandbox">

The Actor creates its sandbox on the first prompt and reconnects to it on every prompt after that:

<CodeSnippet file="examples/docs/run-amp/session.ts" title="session.ts" highlight="provider,sandbox,lifecycle" />

- `e2bProvider` starts sandboxes from E2B's `base` template. E2B stops a sandbox when its timeout runs out, so the one-hour timeout covers a long task, and the provider pauses the sandbox at the timeout instead of deleting it.
- `openSandbox` connects with the stored id. On the first prompt, or after the provider has deleted the sandbox, it creates a new one, saves its id, and clears the thread id. The old thread still exists on Amp's servers, but it talks about files the new sandbox doesn't have, so the next prompt starts a new thread.
- `INSTALL` runs on every connect but returns right away once Amp is installed, so an install that failed partway is retried on the next prompt.
- `onSleep` pauses the sandbox while the Actor sleeps. The next prompt resumes it with its files intact. `onDestroy` deletes it.

<Note>
agentOS can't run Amp, because it only runs software from its own registry, not binaries downloaded with `curl`. Daytona can: pass `daytonaProvider()` from `@rivet-dev/sandbox-adapter/daytona` instead, but Daytona returns a command's output only when it exits, so clients get the events all at once at the end. On Freestyle, the VM's firewall must allow the install script's downloads and the Amp service. See [Providers](/agents/docs/sandboxes#providers).
</Note>

</Step>

<Step title="Run a prompt">

The `prompt` action runs Amp once and streams what it prints:

<CodeSnippet file="examples/docs/run-amp/session.ts" title="session.ts" highlight="prompt" />

- `exec` runs the command in the sandbox's working directory. Its `onData` callback receives output as the sandbox reports it, and `jsonLines` turns that into one event per JSON line.
- Each event is broadcast to connected clients right away, so your app can show tool calls and messages while Amp works.
- The first event, `init`, carries the thread id, which the Actor saves so the next prompt passes it to `threads continue`.
- The transcript gets the prompt and the final answer only after Amp exits cleanly. A failed run throws a `UserError` that the client receives with the reason.
- `c.abortSignal` stops Amp if the Actor shuts down mid-run, and `timeoutMs` stops it if it runs too long.

</Step>

<Step title="Try it">

Register the Actor and start the worker:

<CodeSnippet file="examples/docs/run-amp/server.ts" title="server.ts" />

```sh
npx tsx server.ts
```

In another terminal, connect to a session and send a prompt and a follow-up:

<CodeSnippet file="examples/docs/run-amp/client.ts" title="client.ts" />

```sh
npx tsx client.ts
```

The first prompt takes longer because it creates the sandbox and installs Amp. The follow-up reuses both and continues the same thread, so "it" refers to `fib.py`. Run `client.ts` again later with the same session id and it picks up where it left off. Call `getTranscript` to show the earlier turns.

</Step>

</Steps>
