Run OpenCode for your users in cloud sandboxes, with one Rivet Actor per session that remembers the conversation and the sandbox.

What we'll build:

- An `opencodeSession` Rivet Actor per session, keyed by your session id, that stores the transcript, the sandbox id, and OpenCode's own session id.
- An E2B sandbox per session, created through the sandbox adapter, with OpenCode installed on first use.
- A `prompt` action that runs `opencode run` with `exec` and streams each JSON event to connected clients as it arrives.
- Follow-up prompts that reconnect to the same sandbox and continue the same OpenCode session.

<Steps>

<Step title="Install">

```sh
npm add @rivet-dev/sandbox-adapter e2b rivetkit@3.0.0-preview.1
```

OpenCode itself isn't installed on your worker. Each sandbox installs its own copy.

</Step>

<Step title="Set the keys">

Create an API key in the <a href="https://e2b.dev/dashboard" target="_blank" rel="noopener noreferrer">E2B dashboard</a> and one in the <a href="https://platform.claude.com" target="_blank" rel="noopener noreferrer">Claude Console</a>, then set both on your worker:

```sh
E2B_API_KEY=e2b_...
ANTHROPIC_API_KEY=sk-ant-...
```

The E2B key never enters the sandbox. The Anthropic key reaches only the OpenCode process, as the next step shows. OpenCode works with many model providers, so you can use another provider's key instead.

</Step>

<Step title="Build the command">

`cli.ts` holds everything that is specific to OpenCode: how to install it, how to run it without a terminal, and how to read what it prints:

<CodeSnippet file="examples/docs/run-opencode/cli.ts" title="cli.ts" highlight="command,events" />

- `INSTALL` runs OpenCode's install script, which puts the CLI at `~/.opencode/bin/opencode`. The `test -x` check skips the download when the sandbox already has it.
- `opencode run` runs one prompt and exits. `--format json` prints every text block, tool call, and step as one JSON line.
- `--auto` approves every permission request that the configuration doesn't deny. Without it, `opencode run` rejects any request that needs an answer, because nobody is there to give one. The sandbox is the boundary.
- `--model` picks the model as `provider/model`. To use another provider, change `MODEL` and pass that provider's key in `cliEnv`. Run `opencode models` in a sandbox to list the names.
- `--session` continues the conversation from an earlier run. OpenCode keeps its sessions in its data directory inside the sandbox, so this works for as long as the sandbox exists.
- `readEvent` takes the session id from any event, since every event carries `sessionID`. OpenCode has no final result event, so the answer is the text of the last `text` event.

<Warning>
`cliEnv` passes `ANTHROPIC_API_KEY` in the `env` of a single `exec` call. The provider hands it to that one process, and it is never written to the sandbox's disk. Commands that OpenCode runs inherit it, though, so code in the sandbox can read it. Give the sandbox a key with a spending limit.
</Warning>

</Step>

<Step title="Create the session Actor">

Each session is an `opencodeSession` Actor, keyed by your session id:

<CodeSnippet file="examples/docs/run-opencode/session.ts" title="session.ts" highlight="state" />

- `state` is saved with the Actor, so it survives sleep, crashes, and upgrades. It holds the transcript, the session's sandbox id, and the id OpenCode gave its own session, which is different from your session id.
- `output` is the event that carries OpenCode's JSON events to every connected client.
- `running` lives in `vars`, which are not saved. It stops a second prompt from starting a second OpenCode in the same sandbox while the first one works.
- `actionTimeout` raises RivetKit's 60-second limit on an action, because one coding task can take many minutes.

<Warning>
Any client that knows a session id can prompt it, and every prompt runs commands with your API key. In production, protect the Actor with [authentication](/docs/authentication).
</Warning>

</Step>

<Step title="Connect the sandbox">

The Actor creates its sandbox on the first prompt and reconnects to it on every prompt after that:

<CodeSnippet file="examples/docs/run-opencode/session.ts" title="session.ts" highlight="provider,sandbox,lifecycle" />

- `e2bProvider` starts sandboxes from E2B's `base` template. E2B stops a sandbox when its timeout runs out, so the one-hour timeout covers a long task, and the provider pauses the sandbox at the timeout instead of deleting it.
- `openSandbox` connects with the stored id. On the first prompt, or after the provider has deleted the sandbox, it creates a new one, saves its id, and clears OpenCode's session id, since the new sandbox has none of the earlier files or sessions.
- `INSTALL` runs on every connect but returns right away once OpenCode is installed, so an install that failed partway is retried on the next prompt.
- `onSleep` pauses the sandbox while the Actor sleeps. The next prompt resumes it with its files and OpenCode's sessions intact. `onDestroy` deletes it.

<Note>
agentOS can't run OpenCode, because it only runs software from its own registry, not binaries downloaded with `curl`. Daytona can: pass `daytonaProvider()` from `@rivet-dev/sandbox-adapter/daytona` instead, but Daytona returns a command's output only when it exits, so clients get the events all at once at the end. On Freestyle, the VM's firewall must allow the install script's downloads and your model provider's API. See [Providers](/agents/docs/sandboxes#providers).
</Note>

</Step>

<Step title="Run a prompt">

The `prompt` action runs OpenCode once and streams what it prints:

<CodeSnippet file="examples/docs/run-opencode/session.ts" title="session.ts" highlight="prompt" />

- `exec` runs the command in the sandbox's working directory. Its `onData` callback receives output as the sandbox reports it, and `jsonLines` turns that into one event per JSON line.
- Each event is broadcast to connected clients right away, so your app can show tool calls and text while OpenCode works.
- Every event carries OpenCode's session id, which the Actor saves so the next prompt passes it to `--session`.
- The transcript gets the prompt and the final answer only after OpenCode exits cleanly. A failed run throws a `UserError` that the client receives with the reason.
- `c.abortSignal` stops OpenCode if the Actor shuts down mid-run, and `timeoutMs` stops it if it runs too long.

</Step>

<Step title="Try it">

Register the Actor and start the worker:

<CodeSnippet file="examples/docs/run-opencode/server.ts" title="server.ts" />

```sh
npx tsx server.ts
```

In another terminal, connect to a session and send a prompt and a follow-up:

<CodeSnippet file="examples/docs/run-opencode/client.ts" title="client.ts" />

```sh
npx tsx client.ts
```

The first prompt takes longer because it creates the sandbox and installs OpenCode. The follow-up reuses both and continues the same conversation, so "it" refers to `fib.py`. Run `client.ts` again later with the same session id and it picks up where it left off. Call `getTranscript` to show the earlier turns.

</Step>

</Steps>
