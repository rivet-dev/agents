`@rivet-dev/pi` runs <a href="https://earendil.com/posts/pi-durable/" target="_blank" rel="noopener noreferrer">Pi Durable</a>, Earendil's durable agent harness, inside a [Rivet Actor](/actors/docs). You define the agent once, and every key you call it with gets its own Actor, conversations, and files. Pi Durable saves every conversation, model call, tool call, and task as it happens.

<a href="https://github.com/earendil-works/pi/tree/main/packages/durable" target="_blank" rel="noopener noreferrer">Pi Durable</a> is still in beta, so expect its API to change between releases.
</Note>

- **The agent loop runs in the Actor.** Model calls, retries, and the conversation run in your backend, next to your application code, where you control credentials, permissions, and logging.
- **Files without a sandbox.** By default, the agent's file tools work on files in the Actor's own SQLite database, so there is nothing else to set up.
- **A sandbox when it needs a shell.** Add a sandbox such as E2B or Daytona, and file and shell tools run there. Nothing the agent runs executes on your worker, and your provider keys never enter the sandbox.
- **Agents are durable.** Each agent lives in its Actor's SQLite database, not in memory, so it can sleep, crash, or upgrade mid-run and pick up where it left off.

## Why run Pi on Rivet

### Stateful agents on any infrastructure

- **A live process per agent.** Each agent is an Actor with its own memory and SQLite database. It keeps its conversations loaded between prompts, so two servers never race on the same agent. Nothing is rebuilt from a database or replayed from an event log on each request.
- **No cloud lock-in.** Rivet is open source under Apache 2.0. Use <a href="https://dashboard.rivet.dev" target="_blank" rel="noopener noreferrer">Rivet Cloud</a>, [bring your own compute](/docs/deploy/self-host/workers), or [self-host](/docs/deploy/self-host/control-plane) everything. Workers run on Kubernetes, AWS ECS, Railway, Render, Vercel, Google Cloud Run, AWS Lambda, or any VM.

### Any harness, any model

- **Bring your harness.** Rivet runs existing agent harnesses, starting with Pi, instead of asking you to rewrite your agent for a new framework.
- **Bring your model and keys.** Use any provider the harness supports, [your own API keys](#model-access), or [your users' own subscriptions](/guides/user-subscriptions).

### Built for scale and realtime

- **Lightweight.** A running Actor adds about 72 KB of memory on top of the agent's conversations, and a sleeping agent uses none. Give every user, task, or thread its own agent.
- **Wakes in milliseconds.** A sleeping agent wakes on its next prompt in about 12 ms, instead of the seconds it takes to boot a container.
- **Realtime and multiplayer.** Clients connect over WebSockets and stream events as the agent works. Many users can watch and steer the same conversation.
- **One primitive for your backend.** Agents are Actors, like the rest of your Rivet app, so they call other agents and Actors directly and use the same schedules, queues, and workflows.
- **Swappable sandboxes.** A sandbox crash does not lose the conversation, and a tool call adds about 10 ms in the same datacenter.

## Call the agent

A conversation is one thread of messages inside an agent. Each agent has a root conversation, which `prompt` uses by default, and can hold more conversations. A conversation keeps the full history of messages and tool calls, handles one run at a time, calling the model and tools until the model is done, and streams its changes to every client that watches it. It survives sleep, crashes, and upgrades. See [Architecture](#architecture).

<CodeSnippet file="examples/docs/pi/client.ts" title="client.ts" />

The `prompt` action sends input, waits, and returns `{ status: "done", text }` or `{ status: "unanswered", reason }`. A model error doesn't reject it: a failed model call is retried automatically, and if it keeps failing, `status` is `unanswered` with Pi's reason, and the conversation is kept. The other actions mirror Pi Durable's methods under `harness`, `conversation`, and `submission`, with IDs in place of objects.

| To | Call |
| --- | --- |
| Prompt and wait | `prompt(text, { requestId })` |
| Start a run without waiting | `submit(text, { requestId })` |
| Steer a run | `prompt(text, { whenBusy: "steer" })` |
| Cancel a run | `conversation.abort(id)` |
| Switch models | `conversation.configure(id, { model: { provider, modelId } })` |
| Summarize older messages | `conversation.compact(id)` |
| Get the root conversation | `harness.root()` |
| Start a conversation | `harness.createConversation({ ownership: { kind: "ownerless" } })` |

Actions wait up to ten minutes, and a timed-out wait leaves the run going. Only `abort` stops a run. If `prompt` times out or its client disconnects, `prompt` rejects, and the run keeps going until it finishes. Send the prompt again with the same `requestId` to get its result instead of running the agent twice. `submit` takes the same options as `prompt` and returns `{ submissionId }` at once. Pair it with `onAnswer` to deliver the answer. See the <a href="https://github.com/rivet-dev/agents/blob/main/packages/pi/src/actions.ts" target="_blank" rel="noopener noreferrer">source</a> for every action.

### Steer, follow up, or cancel

On an idle conversation, a prompt runs right away. While a run is in progress, `prompt(text, { whenBusy })` decides what happens to the new prompt:

| `whenBusy` | What it does |
| --- | --- |
| `"followUp"` | The default. The agent reads the message once it has no tool calls left, and the run continues. |
| `"steer"` | The agent reads the message after its current tool calls finish, before its next model call. |
| `"reject"` | The prompt fails with a `ConversationBusy` error, and nothing is queued. |

To cancel a run, call `conversation.abort(id)`. It stops any command still running in the sandbox. Daytona can't cancel a command, so it runs until it exits or times out.

### Compaction

When the context fills up, the agent summarizes older messages and keeps going. Call `conversation.compact(id)` to do it yourself. The conversation keeps working while the summary is written.

## Deliver answers

`onAnswer` runs in the agent Actor for every final answer, with the Actor's context. Use it to send answers somewhere, such as a chat app or a text message, without a client waiting on `prompt`:

<CodeSnippet file="examples/docs/personal-agent/assistant.ts" title="assistant.ts" region="answer" />

- It gets `{ conversationId, text, message }`. Responses that only call tools aren't final answers, so they don't call it.
- It runs inside the run, so an answer that finishes after a crash or restart is still delivered. If the Actor stops while `onAnswer` is running, it can run again for the same answer.
- A throw goes to `onReport` and leaves the answer in the conversation.
- It runs in conversations that use the default extensions. A conversation that selects its extensions by name doesn't get it.

## Stream a conversation

<CodeSnippet file="examples/docs/pi/stream.ts" title="stream.ts" />

The `conversation.watch(id)` action returns `{ value }`, the conversation's view, including a partial answer, so a client that connects late catches up. Then the agent sends `pi.view` frames to that connection only. Each frame has `conversationId`, `seq`, and either `value` or `ops`.

- A frame with `seq` 0 has a `value`, which replaces everything the client had.
- Other frames have Chord operations in `ops`. Apply them to the view with `applyImmutable` from `@earendil-works/chord/delta`, which you install with `npm add @earendil-works/chord`.
- The `seq` number goes up by one for each frame. A gap in `seq` means call `conversation.watch` again.
- To stop listening, call `conversation.unwatch(id)`.

| In the view | What it shows |
| --- | --- |
| `entries` | The newest entries of the transcript, starting with the newest 50. |
| `before` | The id of the entry just before `entries`. It is absent when `entries` reaches the start of the transcript. |
| `docs["pi.live"].run` | Present while a run is in progress. |
| `docs["pi.live"].generation` | The partial answer in `message`, and the retry backoff in `retry`. |
| `docs["pi.live"].tools` | The tools of the current round, each with a `name`, a `status`, and its running `output`. |
| `docs["pi.live"].compactions` | Older messages are being summarized to free up context. |
| `docs["pi.live"].runFailure` | Why the newest run ended without an answer. |
| `docs["pi.inbox"]` | Messages waiting for the current run. |
| `docs["pi.usage"]` | The conversation's token and cost totals. |

To read older entries, pass `before` to `conversation.entries(id, { maxEntryId: before }, limit)`. To read the messages the model sees, call `conversation.context(id)`, which returns `{ messages }`.

## Architecture

Each agent is a Rivet Actor. A run is a series of steps, such as model calls, tool calls, and task phases, and the agent saves each step to the Actor's SQLite database before the next one begins. Each key gets its own agent, with its own conversations, files, and sandbox.

### Sleep

An idle agent sleeps and frees its memory. The next action on its key wakes it: the agent opens Pi from SQLite, resumes interrupted work, and reconnects to the same sandbox the first time a tool needs it, so clients don't do anything different. While the agent sleeps, its sandbox is suspended.

During a retry or poll wait, the Actor also sleeps, and a scheduled wake resumes the work when the wait ends.

### What survives

| | Conversations | Sandbox |
| --- | --- | --- |
| Sleep | Every step so far. | Reconnected on first use. |
| Crash | Every step saved before the crash. A run in progress resumes on wake from the step it reached. | Reconnected on first use. |
| Upgrade | Every step so far. A run in progress gets time to finish first. See [Upgrades](#upgrades). | Reconnected on first use. |
| Destroy | Deleted. | Deleted. |

A model or instructions set with `conversation.configure` are part of the conversation, so they are kept too. Without a sandbox, files live in the Actor's SQLite database and survive the same way as conversations. If the sandbox no longer exists when the agent wakes, a new one is created and the old files are lost.

Actions that don't run a tool, such as `conversation.context` or `conversation.configure`, don't connect to the sandbox. They keep working while the sandbox provider is down.

### Resuming a run

After a crash or a cut-off upgrade, the agent reads the saved steps on wake and carries on from the step it reached:

| Stopped while | On wake |
| --- | --- |
| The model was answering | The call counts as a failed attempt, and the partial answer is saved as a stopped message. The model call is sent again after the retry backoff. With no retries left, the run ends unanswered. |
| A tool marked `replay: "safe"` ran | The tool runs again. |
| Any other tool ran | The tool isn't run again. Its result tells the model the call stopped partway. |
| A task phase ran | The phase runs again, and earlier phases are kept. |
| The run was cancelled with `abort` | Nothing resumes. |

Streamed output is saved in batches, about once a second. A crash can lose about the last second of a partial answer or of a tool's running output. Finished messages and tool results are saved before the run continues.

Nothing runs while a crashed Actor is down. The run resumes when the Actor starts again. A client that is still connected gets a fresh view of the conversation.

### Upgrades

When you ship new code, running work gets up to `sleepGracePeriod` (15 minutes by default) to finish before the Actor restarts on the new version. See [Versions](/docs/versions). Work still running when the grace period ends resumes on wake, after your `onWake` runs.

A client waiting on `prompt` gets an error if the Actor stops first. It can send the prompt again with the same `requestId` to get the first prompt's result instead of a second run.

Destroying the Actor stops running work at once, without a grace period.

Roll forward only. An older version of Pi Durable can't open data that a newer version wrote, so don't roll back after an upgrade has run.

The agent loop runs in an Actor on your backend, and the commands the model chooses run in a sandbox. Everything that needs a secret stays in your backend.

### What reaches the sandbox

- Only calls of the built-in tools: commands to run, and files to read or write. Each agent has its own sandbox. Your [custom tools](/guides/agent-custom-tools) run on your worker.
- Not your worker's environment. Commands run with the sandbox's own environment.
- File tools reject paths outside the working directory. Shell commands can reach anything inside the sandbox, so the sandbox itself is the boundary.
- Without a sandbox, files live in the Actor's own SQLite database and there is no shell, so `bash` returns an error. Commands never fall back to running on your worker.

### Where secrets live

- Model keys, sandbox provider keys, and the secrets your [custom tools](/guides/agent-custom-tools) use stay on your worker. The model and the sandbox never see them.
- [User subscription](/guides/user-subscriptions) logins stay in your `credentials` Actor. The agent never receives a refresh token.
- A conversation stores every message and tool result, and clients can read them with `conversation.context` or watch them as events, so keep secrets out of tool results and error messages.
- [Traces](/guides/agent-observability) never record prompt text, tool arguments, or tool results.

### Who can connect

- Anyone who can connect to an agent can prompt it and read every one of its conversations. Add [authentication](/docs/authentication) and check that the caller may use the agent's key. Keys aren't secret.
- Protect the `credentials` Actor the same way, because its actions return provider tokens.
- Give a browser a short-lived token for one agent instead of your Rivet credentials. See [Client SDK](/guides/agent-client-sdk#browsers).

## Known limitations

- **No automatic `AGENTS.md` or skill discovery.** Load them with prompt sections. See [System Prompt](/guides/agent-system-prompt) and [Skills](/guides/agent-skills).
- **No shell without a sandbox.** `bash` needs a [sandbox](/guides/agent-sandboxes).
- **Plain tool calls aren't rerun after a crash.** Use a task or `replay: "safe"`.
- **A tool that ignores its abort signal blocks sleep.** An upgrade then waits up to `sleepGracePeriod` for it to finish.
- **A cut-off model request is sent again from the start.**
- **No image reads, and no binary writes** in a sandbox.
- **Waits cap at ten minutes.** For longer jobs, use `conversation.submit` and stream.
- **No `db` option.** Keep your data in `state`, documents, or another Actor.
- **No built-in approval flow.** See [Human in the Loop](/guides/agent-human-in-the-loop).
- **Roll forward only.** See [Upgrades](#upgrades).
- **Node.js 22.19 or later.**

Set the key for your model provider in the environment of the process that runs your Actors:

```sh
ANTHROPIC_API_KEY=sk-ant-...
```

Pi reads the provider-named variable, such as `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `XAI_API_KEY`, `DEEPSEEK_API_KEY`, `GROQ_API_KEY`, or `OPENROUTER_API_KEY`. See Pi's <a href="https://github.com/earendil-works/pi" target="_blank" rel="noopener noreferrer">provider list</a> for the rest.

## Configuration

The `pi()` function accepts every [`actor()`](/actors/docs/actor-configuration) option except `db`, plus:

| Option | Description |
| --- | --- |
| `registry` | Required. Your tools and tasks, from `createRegistry()`. See [Bundle Tools and Hooks into Extensions](/guides/pi-extensions). |
| `model` | Starting model of new conversations, as `provider/modelId`. |
| `scopedModels` | Models a client may switch to. |
| `apiKeys` | API keys by provider. See [Keys in code](#keys-in-code). |
| `providers` | Providers Pi does not know. See [Custom providers](#custom-providers). |
| `credentials` | Logins your app stores. See [Run Agents on Your Users' Subscriptions](/guides/user-subscriptions). |
| `sandbox` | Where `CodingTools` run. Without one, files live in the Actor's database. See [Providers](/guides/agent-sandboxes#providers) for each provider's options. |
| `documents` | Documents clients may read. |
| `settings` | Pi Durable settings, such as `retry` and `compaction`. |
| `onAnswer` | Runs for every final answer. See [Deliver answers](#deliver-answers). |

Other options, such as `thinkingLevel` and `env`, pass through to Pi Durable. By default, `actionTimeout` is ten minutes and `sleepGracePeriod` is 15 minutes. A `ConversationBusy` error reaches clients as a `UserError`, and so does `pi_schema_too_new` when the actor's data has a newer Pi Durable schema than the code. Other Pi Durable errors reach clients as internal errors.
