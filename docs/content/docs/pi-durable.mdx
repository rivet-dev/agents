## What durable means

A run is a series of steps: model calls, tool calls, and tasks your tools define. Each step is saved to the Actor's SQLite database before the next one begins, so after a crash the run carries on from the step it reached.

- **Tools can launch tasks.** A task splits work into phases and saves each one before the next starts.
- **Cancelling cleans up.** Cancelling a tool call cancels the tasks it launched, and their `abort` handlers can undo the work.

## When to use Pi Durable

Use `piDurable()` when a run has to finish with nobody there to retry it:

- **Background work**, such as jobs, schedules, and webhooks.
- **Multi-step side effects**, such as payments or pull requests.
- **Retrying callers.** A prompt resent to a conversation with the same `requestId` runs once.
- **Many conversations per agent**, such as forks or subagents.
- **Many clients watching one run**, including late joiners.

For chats a person drives, use [Pi](/agents/docs/pi#when-to-use-pi). To get started, see the [Quickstart](/agents/docs/quickstart).

## Tools and tasks

`CodingTools` adds `read`, `write`, `edit`, and `bash`, which run in the [sandbox](/agents/docs/sandboxes). Your own tools and tasks run in your backend. For multi-step work with side effects, launch a task from the tool:

After a crash, the task reruns its current phase, and the idempotency key prevents a double charge. Cancelling the run calls `abort`, which refunds it. A plain tool call cut off by a crash isn't rerun unless it's marked `replay: "safe"`.

## Call the agent

`prompt` sends input, waits, and returns `{ status: "done", text }` or `{ status: "unanswered", reason }`. The other actions mirror Pi Durable's methods under `harness`, `conversation`, and `submission`, with IDs in place of objects.

| To | Call |
| --- | --- |
| Prompt and wait | `prompt(text, { requestId })` |
| Start a run without waiting | `conversation.submit(id, { type: "input", content, requestId })` |
| Steer a run | `prompt(text, { whenBusy: "steer" })` |
| Cancel a run | `conversation.abort(id)` |
| Switch models | `conversation.configure(id, { model: { provider, modelId } })` |
| Get the root conversation | `harness.root()` |
| Start a conversation | `harness.createConversation({ ownership: { kind: "ownerless" } })` |

Actions wait up to ten minutes, and a timed-out wait leaves the run going. See the <a href="https://github.com/rivet-dev/agents/blob/main/packages/pi/src/durable/actions.ts" target="_blank" rel="noopener noreferrer">source</a> for every action.

## Moving from `pi()`

| With `pi()` | With `piDurable()` |
| --- | --- |
| `customTools: [tool]` | Pi Durable's `defineTool`, installed with `defineExtension` |
| Pi's built-in coding tools | `registry.install(CodingTools)` |
| `prompt`, then `getLastAssistantText()` | `prompt(text, { requestId })`, which returns the text |
| `prompt` throws during a run | `prompt` queues as a follow-up |
| `conn.on("event", ...)` | `conversation.watchEvents(id)`, then `conn.on("pi.events", ...)` |
| `AGENTS.md` and skills | System prompt sections you add yourself |

Existing `pi()` conversations don't carry over, so give the `piDurable()` agent a new Actor name.

## Upgrades and crashes

- When you ship new code, running work gets up to `sleepGracePeriod` (15 minutes) to finish before the Actor restarts.
- Anything cut off resumes from its last saved step, after your `onWake` runs.
- Destroying the Actor stops it immediately.

See [Architecture](/agents/docs/architecture#pi-durable).

## Known limitations

- **Beta API.** Install `@earendil-works/pi-durable` yourself (`^1.0.2`), and test upgrades before shipping.
- **No skills, `AGENTS.md`, or session tree.** Use system prompt sections and `conversation.fork`.
- **Plain tool calls aren't rerun after a crash.** Use a task or `replay: "safe"`.
- **Tools must honor their abort signal**, or they keep the Actor awake and delay upgrades.
- **A cut-off model request is sent again from the start.**
- **No image reads or binary writes** in the sandbox.
- **Waits cap at ten minutes.** For longer jobs, use `conversation.submit` and stream.
- **Only `prompt` is traced** in [Observability](/agents/docs/observability).
- **No `db` option.** Keep your data in `state`, documents, or another Actor.
- **No built-in approval flow** like [Human in the Loop](/agents/docs/human-in-the-loop).
- **Roll forward only.** An older Pi Durable can't open data a newer one wrote.
- **Node.js 22.19 or later.**

## Configuration

`piDurable()` accepts every [`actor()`](/actors/docs/actor-configuration) option except `db`, plus:

| Option | Description |
| --- | --- |
| `registry` | Required. Your tools and tasks, from `createRegistry()`. |
| `model` | Starting model of new conversations, as `provider/modelId`. |
| `scopedModels` | Models a client may switch to. |
| `apiKeys`, `providers`, `credentials` | Model access, as for [Pi](/agents/docs/pi#configuration). |
| `sandbox` | Where `CodingTools` run. See [Sandboxes](/agents/docs/sandboxes). |
| `documents` | Documents clients may read. |
| `settings` | Pi Durable settings, such as `retry` and `compaction`. |

Other options, such as `thinkingLevel` and `env`, pass through to Pi Durable. `ConversationBusy` reaches clients as a `UserError`, and other Pi Durable errors as internal errors.
