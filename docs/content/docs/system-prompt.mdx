An agent's system prompt is built from prompt sections. Your extensions add sections that every conversation gets, and a conversation can add its own `instructions` after them. The agent renders the system prompt again before every model call.

## Sections for every conversation

Add sections with an extension. A section is a key and a function that returns its text:

<CodeSnippet file="examples/docs/system-prompt/server.ts" title="server.ts" />

The model gets each section as a block tagged with its key:

```text
<role>
You review pull requests for the payments team. Be brief and cite file paths.
</role>
<date>
Today is Mon Oct 12 2026.
</date>
<agents_md>
Run `npm test` before proposing a fix. Never edit files in `migrations/`.
</agents_md>
```

- **Sections render before every model call.** A section can return text that changes, such as the current date, a file, or a value from your database.
- **Order follows the conversation's extensions,** which is install order by default. See [Extensions](/agents/docs/extensions).
- **Return `undefined` to leave a section out.** Pass `{ tag: false }` as the third argument of `section()` to send the text without the tags.
- **A section that throws keeps its previous text.** The model keeps what it already had, and the error is reported.
- **`wrapSection`** changes a section from another extension by its key. See [Wrap a tool](/agents/docs/extensions#wrap-a-tool).

## AGENTS.md

Pi doesn't read `AGENTS.md` on its own. Load it with a section, as `agents_md` does above. The section gets the conversation's workspace as `input.env`, the same files Pi's `read` tool sees: the [sandbox](/agents/docs/sandboxes), or the files in the Actor's database when there is no sandbox. An edit to `AGENTS.md` reaches the model on its next call.

With a sandbox, reading the file connects the sandbox on the first model call instead of the first tool call.

## How changes reach the model

The agent records a change to the system prompt in the conversation, at the point where it changed. After a restart, and in a fork, the conversation has exactly the system prompt the model saw at each point. On models that accept system prompt changes in the middle of a conversation, only the change is sent, so the provider's prompt cache stays valid.

## Instructions for one conversation

Call `conversation.configure(id, { instructions })` to give one conversation its own instructions. They go after every extension section, and they apply from the next model call. Pass `instructions: null` to remove them.

## Context for one prompt

Put context for a single turn in the prompt itself. The `prompt` action takes a string, or an array of text and image blocks. Each image is `{ type: "image", data, mimeType }`, with the image base64-encoded in `data`. The system prompt stays the same.
